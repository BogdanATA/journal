## Phase Goal

**As a** person who remembers writing something last Tuesday, **I want to** open a calendar, see which days I actually wrote on, and jump straight into that day to edit it, **so that** nothing I have written is ever locked away just because the day ended.

<objective>
Deliver the navigation half of Phase 1: a hand-rolled month-grid calendar that marks days with entries, opens from both a button and a keyboard shortcut, and drops the user into any past day on the same editing surface they use for today — plus the one destructive action in the app, deleting a whole day, guarded by a confirmation dialog.

Purpose: NAV-01 and NAV-02 are what turn a daily scratchpad into a journal. D-08 is the load-bearing constraint — a past day must feel identical to today, because a separate "past day mode" would be a second interaction model to learn and a second code path to keep correct. The only asymmetry is the file that gets loaded.

Output: calendar navigation wired through the existing `goToDay` flush-then-load seam, and a delete-day flow whose confirmation exists specifically because there is no cloud backup (D-09).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| calendar UI (user-selected date) → `plugin-fs` path arguments | The first place in the app where a user action, not the system clock, determines which file is touched. |
| delete affordance → irreversible filesystem removal | The only destructive operation in the app; there is no backup, no trash, and no undo. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Tampering | `src/storage/dayDelete.ts` path argument | high | mitigate | `deleteDay` takes a `Date` and derives its path solely from `dayFilePath(date)`, which throws on any non-`Date` or invalid `Date`. The calendar passes `Date` objects constructed by `date-fns` from the rendered month grid — no free-form filename input exists anywhere in the UI. The capability scope from Plan 01 confines `fs:allow-remove` to the journal folder as the second layer. |
| T-01-10 | Repudiation (irreversible user action) | delete-day flow in `src/app/App.tsx` | high | mitigate | A native confirmation dialog naming the exact date gates the removal, with cancel as the default (D-09). Confirmation is scoped to whole-file deletion only: a verify gate asserts exactly one confirmation call site exists in `src/`, so ordinary editing cannot silently acquire a prompt and, more importantly, no other destructive path can appear without one. |
| T-01-11 | Tampering | `dayIndex` scan reading every day file | medium | mitigate | The scan filters names through `dayFromFileName`'s anchored pattern before reading, so a stray file dropped into the journal folder is ignored rather than read and surfaced. A per-file read failure is caught and that day skipped, so one unreadable file cannot break navigation to every other day. |
| T-01-12 | Denial of Service | `loadDaysWithContent` reading every file on calendar open | low | accept | The scan reads every day file each time the calendar opens, which is linear in days written. At a personal journal's scale — hundreds of small files after years — this is imperceptible, and a persistent index would mean a second source of truth that could disagree with the folder, which is exactly the failure D-07's live-scan design avoids. Revisit only if a real user reports calendar lag. |
</threat_model>
