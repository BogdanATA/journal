## Phase Goal

**As a** person on either a Mac or a Windows PC, **I want to** download and open Journal as a real desktop app despite it being unsigned, **so that** I can use it without a developer account standing between me and my own notes.

<objective>
Turn the working app into installable artifacts on both target platforms, and document the first-launch friction that the unsigned-build decision (D-10/D-11) deliberately accepts.

Purpose: PLATFORM-02 cannot be satisfied on this machine. RESEARCH.md Pitfall 3 is unambiguous — Tauri's own guidance treats macOS-to-Windows cross-compilation as a last resort, and this development machine is macOS-only with no Windows VM. That turns PLATFORM-02 from "run tauri build" into "set up CI", which is a planning fact, not something to discover mid-execution. The README half exists because an unsigned build without documented bypass instructions is, from a user's point of view, a broken download.

Output: a two-OS GitHub Actions matrix producing a macOS `.dmg` and a Windows `.msi`/`.exe` on every push, plus a README that gets a stranger from download to first launch on either platform.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → published build artifact | The workflow compiles code and produces a binary that users will run with an OS warning suppressed. |
| distribution channel → end-user machine | Unsigned installers, downloaded and launched past Gatekeeper and SmartScreen. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Spoofing | unsigned macOS and Windows installers | medium | accept | Accepted product decision (D-10/D-11): no Apple Developer Program enrollment and no Windows code-signing certificate for a free, public, clone-and-build project. Compensating controls rather than mitigation: the README states plainly what the OS warning does and does not mean, `SHA256SUMS.txt` lets a user match a download to the CI build that produced it, and building from source is offered as the alternative for anyone unwilling to trust a binary. Revisit only if distribution scale changes, per D-11. |
| T-01-14 | Tampering | `.github/workflows/build.yml` action supply chain | high | mitigate | Every `uses:` entry is a first-party `actions/*` action; no third-party action is introduced into a workflow that produces a binary users run unsigned. The preinstalled runner Rust toolchain is used instead of a third-party toolchain action. `npm ci` against a committed `package-lock.json` pins the exact dependency tree that was audited in RESEARCH.md rather than resolving fresh ranges at build time. A verify gate fails the task if a non-`actions/` `uses:` appears. |
| T-01-15 | Tampering | build integrity between CI and the user | medium | mitigate | Each matrix leg emits `SHA256SUMS.txt` alongside its installers and uploads it in the same artifact, so a user can confirm the file they downloaded is the file CI produced. This is the only integrity signal available without code signing, which makes it load-bearing rather than decorative here. |
| T-01-16 | Information Disclosure | workflow logs and artifacts | low | accept | The build has no secrets — no signing identity, no notarization credentials, no API keys — so there is nothing for a log or a fork's pull-request run to leak. Accepted with no control precisely because the unsigned decision removed the secret. |
</threat_model>
